# WinSetup Lite

**面向 Windows 的软件安装与开发环境恢复工具**

WinSetup Lite 已实现软件清单导入导出、批量安装和 Python 环境配置。下一阶段将这些能力接入同一条换机流程。**旧电脑导出一份软件和开发环境清单，新电脑导入并确认一次，程序根据本机条件恢复工作环境，并逐项验证结果。** 用户可以知道哪些软件已经装好、哪些环境实际能运行，以及还有哪个条件需要处理。

## 为什么值得做

换电脑时，装好 Git 和 VS Code 只完成了一部分工作。以 PyTorch 项目为例，新机器还要具备合适的 Python、相互兼容的依赖，以及满足要求的显卡和驱动。安装报错时，用户往往要自己找解释器、核对软件源、读日志、换方案，再运行一遍验证。

WinGet 已经提供软件清单导入导出，`winget configure` 也能配置并检查声明的系统状态。WinSetup Lite 复用它安装 Windows 软件，并计划把软件安装、Python 环境重建和异常处理接成一次换机任务。项目要验证的是，**当旧方案无法直接复用时，能否根据新电脑的检查结果减少人工排查，同时满足原先的版本与硬件要求。** [WinGet Configuration](https://learn.microsoft.com/windows/package-manager/winget/configure)

## 已完成的工程工作

| 模块 | 当前实现与验证方式 |
| --- | --- |
| **软件清单** | WinGet 扫描可以匹配到的软件，用户勾选后导出 JSON。清单按软件包 ID 去重，兼容 v1 和 v2。导入后可以检查缺失项，再进入安装。当前清单保存软件名称和 ID。 |
| **自动安装与恢复** | 用户授权后，程序以精确 ID 调用 WinGet，跳过已经安装的软件。下载暂时失败时可以重试，软件源异常时可以刷新后再试。全自动模式会在安装后复查软件状态。 |
| **Python 环境配置** | AI 可以根据用途从 20 种常用库中生成依赖方案。程序用当前 Python 创建独立 `venv`，通过环境内的 `pip` 安装，最后运行 `pip check` 和导入测试。 |
| **PyTorch 专用流程** | 已内置 PyTorch 2.9.1 及配套版本，支持 CPU、必需 NVIDIA CUDA，以及用户明确允许时的 CPU 回退。在目标设备上完成一次张量运算，才将环境标记为已验证。 |
| **本地 AI 接入** | 默认通过 Ollama 使用 Qwen3 1.7B。模型生成结构化的软件或依赖建议，也可以读错误摘要，在重试、刷新软件源、停止等当前操作中提出建议。 |

当前代码通过 **32 项自动测试**，覆盖旧清单兼容性、安装验证、重试、依赖冲突和 GPU 回退条件。测试使用模拟接口。真实 Windows 换机成功率、GPU 兼容性和 AI 排错收益需要通过下一阶段的实测确认。

## 下一阶段如何落地

### 1. 用同一份清单表达恢复目标

清单扩展为三个部分。旧版清单继续作为仅含软件的换机任务使用。

| 内容 | 记录什么 | 恢复时怎么用 |
| --- | --- | --- |
| **软件** | WinGet ID、显示名称，以及用户明确指定的软件版本要求 | 查新电脑是否已有符合要求的版本，缺失时才安装。 |
| **开发环境** | Python 版本要求、直接依赖、旧机实际解析出的包版本、CPU 或 GPU 要求 | 优先尝试旧机的可用组合。新电脑上探测解释器并重建环境，避免依赖旧机的绝对路径。 |
| **调整范围与验收** | 哪些版本锁定、哪些允许变动、能否回退到 CPU、需要通过哪些检查 | 在开始前形成一份可核对的方案。任何调整都必须符合已确认的条件。 |

优先读取用户选定项目的依赖文件。如果只有旧环境，就读取它的解释器和已装包生成快照。在新电脑上重新创建虚拟环境。软件安装清单与个人文件、软件设置和账号数据的备份分别处理。 [Python 虚拟环境文档](https://docs.python.org/3/library/venv.html)

### 2. 把恢复步骤做成有依赖关系的任务

新电脑导入后，先检测软件、Python、系统架构、显卡和驱动，再显示计划。每项任务有明确的前置条件。例如，确认解释器后才能创建虚拟环境，依赖装完后才能做运行验证。Git 安装失败时，如果 PyTorch 环境不依赖 Git，仍可以继续配置。

本地进度文件按清单标识和任务 ID 记录已验证的结果、当前错误和尝试次数。重新打开程序时，先复查以前成功的项目，再处理未完成项。报告区分**已存在、安装成功、验证通过、受阻**。像管理员权限确认或重启这样的系统操作，记录为待处理，完成后再恢复相关任务。

### 3. 让 AI 根据本机证据调整方案

确定性的步骤由程序执行，例如跳过已安装的应用、使用符合要求的解释器、处理明确的网络超时。原因不明确时，AI 可以发起检查，程序执行后把结果反馈给模型。

| AI 可以请求的操作 | 程序返回的证据 |
| --- | --- |
| 列出已安装的 Python 解释器，核对本次选择 | 解释器路径、版本、架构 |
| 查询 NVIDIA 驱动和目标环境的运行状态 | GPU 是否可见、驱动信息、目标环境中的 CUDA 验证结果 |
| 读取本次安装错误，在候选配置中检查兼容性 | 软件源、退出码、错误摘要、兼容安装包是否可找到 |
| 采用符合范围的候选方案并复验 | 实际采用的解释器、包版本、安装和运行结果 |

模型只提交结构化的工具请求，由程序校验参数与用户授权后执行。出现依赖冲突时，模型可以选择候选，依赖能否解析由 `pip` 检查。可用 `pip install --dry-run --report` 在目标解释器下试解析候选组合，再安装并跑验收。项目界面记录**为什么调整、调整了什么、验证结果如何**。 [Ollama 工具调用文档](https://docs.ollama.com/capabilities/tool-calling) · [pip 安装报告](https://pip.pypa.io/en/stable/reference/installation-report/)

例如，清单锁定 PyTorch 2.9.1 和 NVIDIA GPU，但允许调整 CUDA 构建。若旧机的 CUDA 12.8 构建在新机上导入成功、GPU 运算失败，助手先读错误和驱动信息。若本机条件符合 CUDA 12.6 构建的要求，可以在独立环境中测试该构建，再跑同一项 GPU 运算。验证报告记录具体换了哪个构建、用了哪个解释器、GPU 运算是否通过。PyTorch 2.9.1 官方同时提供这两种构建，能否运行取决于本机情况。 [PyTorch 安装文档](https://pytorch.org/get-started/previous-versions/#v291)

### 4. 用实际运行结果验收

Windows 应用通过 WinGet 复查。Python 环境执行依赖一致性检查和实际导入。如果要求 NVIDIA GPU，就在目标环境里做一次 CUDA 张量运算。用户提供了项目测试时，再单列项目是否通过。比如，CPU 依赖导入通过、CUDA 运算失败时，报告会显示基础依赖可用、GPU 目标未完成。

## 怎样证明 AI 带来了增量

下一阶段先做 **Git、VS Code 和一个 PyTorch 环境** 的完整恢复。用同一份清单还原相同的 Windows 初始状态，一组使用固定检测与恢复规则，另一组用同一套执行工具加上多步 AI 排错。两组共享安装源、候选范围和验收项，以便观察差异是否来自排错决策。

| 测试场景 | 观察什么 |
| --- | --- |
| 已装 VS Code，其他条件满足 | 两组都跳过 VS Code，按原计划恢复。 |
| PyTorch 找不到兼容安装包，机器上存在满足要求的候选组合 | 记录模型实际查询了什么、根据哪条证据改变了方案，以及调整后是否通过原验收。单纯重复同一安装命令不计为方案调整。 |
| 清单强制要求 GPU，机器没有可用的 NVIDIA GPU | 记录为 GPU 目标未完成，已恢复的软件仍然保留。 |
| 恢复中途退出后重开 | 检查能否识别已完成项，并从剩余任务继续。 |

记录**通过的验收项、人工干预次数、恢复耗时和是否违反清单约束**。模拟故障用于检验流程，真实性能以 Windows 实测为准。

## 运行当前版本

在 Windows 11 项目目录打开 PowerShell，使用带 Tkinter 的 Python 3.11 或更新版本。运行以下命令启动程序。

```powershell
winget --version
python -m winsetup
```

使用 AI 时，启动本机 Ollama，运行 `ollama pull qwen3:1.7b`。测试命令为 `python -m unittest discover -s tests -v`。
